# 推演分工名单

开推前用独立名单约定每条用例由谁推演。适用于后端、Web、App 三端静态推演。不替代用例本身，也不写入用例文件。用例设计不参与本流程。本技能是分工全文；各端推演流程技能只引用，不复制条文。

## 1. 名单产生与开推门槛

- 名单由三端共识后交给用户确认；用户审核通过前不得开推。
- 各端开推前须先向用户确认本次代码仓库（及分支），再拉最新代码。
- 名单一次标齐所有端后再提交审核，不先出空表再认领，也不分端先后补标。
- 名单经用户审核通过后，各端按自己的端直接开推，不必再走一轮认领；有争议再停。

## 2. 名单是唯一依据

- 分工不写进用例，不靠用例里的「业务端」字段判断该不该推。该字段可保留，但不参与推演分工。
- 名单按条显式标注「推演负责」，取值固定为 `web`、`app`、`后端`，多端并列（如 `web、后端`、`app、后端`）。禁止用「前端」统称，禁止「Web前端」「安卓」等混用。
- 入口在哪端就标哪端：Web 用例不自动派给 App，App 用例不自动派给 Web，也不默认「前端几乎都要推」。无页面入口、仅 Job/协议、仅某一端、明确不需要某端的，也必须写出。
- 各端只推名单上标了本端、且用例本身不是不测的条目。没标本端的，或用例本身标注不测的，推演结果一律记「跳过」，不写「不测」。备注写明原因：按名单由哪端负责，或用例不测。不得因漏标或「业务端」自行加推。
- 「跳过」合并所有本端不推的情况（含名单未标本端、用例不测），只计一类，不再分列结果或分列计数。
- 发现名单标错，先同步三端并再交用户确认后改名单，不要私下各改各的。

## 3. 文件与格式

- 一份用例版本对应一份名单，文件名带用例版本。
- 名单须绑定用例版本号。
- 每条至少包含：用例编号、标题、推演负责、备注（可选）。
- 同一需求若有多个代码仓库，不在名单里用项目列替代确认；各端开推前向用户确认本次仓库即可。
- App 默认 android、iOS 都推；若某次只要一端，在负责栏或备注写清 `android` / `ios`。

## 4. 一条多端时的职责边界

- 各端只判本端职责，按本端对用例预期独立下结论。
- 互不等待、不互相改结论、不替对方下结论；通过/失败不合并。
- 预期若前后端混在一条里，报告里写清本端覆盖到哪。
- 后端只推标了「后端」的条，按后端实现链路判断后端该负责的部分。
- Web / App 只核本端：入口、请求是否发对、返回后是否按接口数据正确渲染/隐藏/置灰等。不审后端下发字段是否正确，也不把「接口可能没下发」写成前端不通过。
- 需要对一下「同一条件下接口会下发什么」时可以对，但这不是会签，也不是出报告的前置门槛。

## 5. 用例升版

- 升版后按改动的用例再出一份名单，写明从哪版到哪版，以及每条属于新增、修改、删除，或仅文案/仅优先级变更。
- 升版名单仍须一次标齐负责端，并经三端共识、用户审核通过后再开推；不是先出空表再认领。
- 步骤、预期、前置、数据变了的，由对应端按新名单重推；未改动且代码也没变的旧条沿用上一版结论，不必重推。
- 只改优先级或模块名、且用户未下令重出报告的，不必重推。
- 用户下令全量重推时，按当时已审核名单全量执行。
- 删除的用例从新名单和新报告中去掉。
