# Web 前端静态推演流程

仅做**浏览器 Web 前端**静态推演（HTML/CSS/JS 与常见 Web 框架）。不替代黑盒；不改业务代码；不跑应用/浏览器实机验证；不做后端/App/小程序/跨端非 Web 链路。路径里没有的调用链不许编造。

业务内容字段、判定口径与交玲玲成稿约定见技能「前端静态推演报告」；本技能管**怎么推、怎么判**。

## 1. 开推前
1. 拿到用例版本、仓库/分支、页面/模块入口范围；入口或材料不清先问。
2. 按技能「推演分工名单」执行：须有三端共识且经用户审核通过的名单；开推前向用户确认本次代码仓库后再拉代码。只推名单标了「web」、且用例本身不是不测的条目；没标「web」的，或用例本身标注不测的，一律记「跳过」，备注写明原因（名单中由哪端负责，或用例不测）。不再单列「不测」。不以「业务端」或名单漏标自行加推。全文见该技能。
3. **先拉取最新代码**，记录分支与 commit；禁止用过时副本开推。
4. 以用例为锚点逐条推；用例标「待补」的代码字段由推演时从仓库补全。
5. 有页面入口：一律追到返回处理与数据展示（用例只验请求不验展示时可止于请求）。无页面断言（如仅 Job/TD-only）可只追到请求或整段跳过。
6. 内网仓/资源经可达网络（常为本机）访问。

### 1.1 全量推演工作流
用户只需一句话下令开始推演，不必事先切分用例子集。接到指令后自行组织执行，**不得要求用户先拆批**。名单未通过用户审核、或尚未向用户确认本次代码仓库前，不得开推。
- 分批前按「推演分工名单」筛出未标「web」的条目，以及用例本身标注不测的条目，一律记跳过、不纳入可推条数。每批 20 条按可推用例计。跳过条目在报告中按用例顺序保留，不计入共/通过/失败。
- 按用例顺序每批固定 **20** 条逐条推演（末批不足 20 条按剩余条数）。
- 每条仍须写出完整链路，禁止用模块套话或「与某条相同 / 同上 / 同一逻辑」省略（见 §2）。
- 全部批次完成后，按用例顺序汇总为**同一份**报告再交玲玲。
- 分批仅为执行组织，不得用模块汇总代替逐条结论，也不得按批次分别交付多份正式报告。

## 2. 完整链路与节点
- 典型检查顺序（仅表示追线步骤，不是报告写法）：页面/模块入口 → 是否可见可操作 → 事件绑定 → 前端校验 → 条件判断 → 状态变化 → API 调用 → 返回处理 → 刷新/跳转/提示/展示。
- **写法（2026-11-13 起）**：报告中的「链路推演」用**序号列表**写出，**不再用箭头（`→`）串联**。每步写「模块/方法，作用」，并带源码路径与行号（入口证明与节点定位仍须可核对）。参考如下：

1. xxx模块1/xxx方法1，xxx作用1
2. xxx模块2/xxx方法2，xxx作用2
3. xxx模块3/xxx方法3，xxx作用3

- 节点示例：

1. OrderListPage.search（OrderListPage.vue:xxx），触发查询，组装筛选参数并发列表请求

- **每个节点写清作用**（做什么、为何存在），并带方法名与源码路径行号；禁止只列文件/函数名或空跳转。
- 按用例顺序逐条写结论，不按模块汇总代替逐条。
- **禁止用「与某条相同」省略完整链路**：即使两条用例链路相同，也必须把完整链路（含入口证明、各节点作用、路径行号等）原样复制写出。禁止用「与 #140 同一确认页逻辑」「与某条相同」「同上」「同一逻辑」这类省略语句代替。每条用例的「链路推演（含入口证明）」都必须是自包含的完整文本。
  反例：用例 145 的「链路推演（含入口证明）」写成「与 #140 同一确认页逻辑。」——即使实际路径相同，也不允许这样写。

### 2.1 警示：入口必须是实际挂载路径
追入口时，**不能按文件名、功能名或文案就近取组件**，必须先证明该组件会被用例对应的产品/域名/角色实际渲染。核证完才能往下追、才能下结论。

1. **引用核证**：全仓检索 import、路由注册、组件注册。全仓无引用的文件是死代码，**不得作为入口，也不得作为通过或失败的依据**。
2. **动态映射要算出回落**：页面用组件表、工厂或配置 key 选组件时，按用例条件（默认域名、角色、环境等）算出实际 key；表中没有该 key 时，跟回落/默认组件，不要跟仓库里「看起来同功能」的另一份实现。
3. **分清外链与站内路由**：入口可能是 `window.open` 打开外站公开页，而不是 `router.push` 站内路由。仓库里若另有未引用组件走站内路由，不得拿它替代真实入口。

反例（曾因此误判失败）：登录页页脚「型号支持」实际由默认登录组件外开共用公开站；仓库里另有一份未被引用的页脚组件会 `push` 站内路由。跟了未引用文件，就把应通过的条目判成失败。

## 3. §六 前端静态规则（适用则全做）
核心检查目标：**用户交互、页面状态、数据请求、返回结果处理、数据展示、前端自行负责的边界和业务判断**。

### 6.1 交互链路
检查顺序：页面/组件 → 可见 → 可操作 → 事件绑定 → 前端校验 → 条件判断 → 状态变化 → API → 返回处理 → 刷新/跳转/提示/组件状态。落笔时仍按 §2 用序号列表写链路。
检查：组件是否存在且**是否被实际引用/挂载**（见 2.1）、是否处在用例要求的页面状态、控件是否可用、事件是否真正绑定、是否调预期方法与正确 API、请求参数是否正确、成功后状态是否更新、失败是否显示预期提示、有无错误禁用/隐藏/条件渲染。

### 6.2 数据展示链路
检查顺序：接口响应字段 → 前端转换/适配 → 组件或 Vuex/Pinia 状态 → 列表/表单/详情绑定 → 格式化/枚举/权限/条件渲染 → 用户最终看到的数据。
检查：字段名与读取是否正确、有无错字段、枚举映射、日期金额状态格式化、错误过滤、条件渲染未显示、空值默认值、列表分页详情表单展示是否正确。

### 6.3 边界与前端校验
用例明确要求的前端边界须查：输入长度、数值范围、必填、格式、空值、重复提交、禁用状态、前端条件分支、错误提示、**请求发出前是否阻止非法操作**。
即使用例未明确要求前端边界，若仅后端校验而前端仍允许提交非法输入 → **未完整实现**（=失败）。

### 6.4 文案 / i18n
若项目构建时注入翻译（如 `pull_translations`），不以仓库语言包缺 key 单独判「露文案」失败；文案以构建注入后现网为准。区分仓库静态与构建后结果。

## 4. 事务 / 权限 / 异常（§八 · 前端负责部分）
- **事务与一致性**：仅用例明确要求全部成功/回滚、批量一致、异常不部分写入、多状态载体同时成功等时才强制查；前端侧重点是异常后页面是否部分更新、与后端失败响应联动的 UI 一致性。
- **权限**：仅用例明确涉及登录用户、角色、租户/数据权限/范围、越权时查前端权限控制（隐藏/禁用/路由守卫等）；未明确不扩大。
- **异常失败链路**：预期含参数校验失败、业务异常、权限拒绝、错误提示、失败响应、异常状态时，异常路径即目标链路：异常触发 → … → HTTP/RPC 响应 → 前端错误处理 → 错误提示或页面状态（落笔时仍按 §2 用序号列表写链路）。

## 5. 动态逻辑（§九 · 前端负责部分）
优先分析源码、注解、配置、路由、依赖注入、工厂映射、生成规则、环境配置。第三方库默认可信，只查项目自定义代码/封装/配置/参数与返回值处理。
- **实现缺口**：代码在、路径缺（含 Vue 动态组件关键配置缺失、用例缺分支输入导致无法确定实际路径）→ **未完整实现** / 失败。
- **材料/环境阻断**：读不到源码或缺关键文件 → 见下方判定（计入失败，非「待补通过」）。仅关键运行时信息确实缺失才保守结论。

## 6. 判定与级别
- **未完整实现** = 失败并计入失败数。
- **缺材料**：失败；原因「缺少材料xxx」；计入失败；该条标题左侧「优先级」与用例优先级一致，不再一律标 P2。
- 用例只验请求不验展示 → 不必验展示。
- **全链路通过才算通过**；仅按用例预期判定。不把未推演写成通过。
- 结论计数：共 x / 通过 y / 失败 z；有跳过另记跳过条数，不计入「共」。不再另记「不测」。没标「web」的，或用例本身标注不测的，一律记跳过，备注写明原因（名单中由哪端负责，或用例不测）。
- **优先级与对应用例优先级一致（2026-11-17 起，字段/排版）**：在每条标题左侧用气泡/徽章展示「优先级」，取值与该条用例优先级保持一致（用例是 P几就标 P几）。通过条目也展示用例优先级，不要写「无」。不要再自行按「P1系统崩溃 / P2主要功能不可用 / P3次要功能 / P4建议」定级。逐条删除「问题级别」字段（通过时也不再写「无」）。用例未标优先级时先问清，不得自行补级。过滤/搜索栏与「导出表格」CSV 对应列由「问题级别」改为「优先级」（过滤支持多选）。字段排版细节见「前端静态推演报告」。
- **不通过原因的已实现 / 未实现（2026-11-13 起）**：用例推演结果不通过，且预期结果部分已实现、部分未实现时，在「不通过原因」中分别标注**已实现内容**和**未实现内容**。切分依据是**用例预期结果**，**不按代码里有哪些方法切分**。
  - **已实现**：只写预期结果里实际已满足的部分。预期完全未满足时，不要为了凑格式，把「代码做了别的事」写成已实现。
  - **未实现**：只写预期中尚未满足的缺口，一句能说清就一句。禁止把已实现那句原样或扩写后再贴进未实现。不要把链路里已经写过的实现细节、注释原文、文案对照、库约束假设再堆进原因。
  - 禁止把原不通过原因在逗号处机械切开，或把整句原文复制到未实现里。
  - 反例：用例要求忽略大小写判重，代码只做了精确相等查重。错误写法是「已实现：checkName() 按名称精确相等查重。未实现：checkName() 按名称精确相等查重，……（再跟一段实现细节）」。正确写法是「未实现忽略大小写判重」。

## 7. 协作要点
- 与用例设计师对齐预期变更后再改判/重推。
- 黑盒失败涉页面/前端链路时再介入定位；接口/落库交后端同事，App 交 App 推演同事，设备 TCP 交设备模拟同事。
- **最终 HTML 成稿交「玲玲（UI设计）」**：全部批次完成并按用例顺序汇总为同一份报告后，把结构化链路/结论/缺陷与优先级/证据一次性交玲玲排版；不得按批次分别交付多份正式报告。玲玲不写不补业务内容。自己可留草稿核对，群内/对外最终报告以玲玲成稿为准。
- 交玲玲的材料中，「失败清单摘要」只对整体失败用例做简单概述，**不得逐条罗列每条失败用例说明**（详见「前端静态推演报告」技能）。
- 群内只发实质结论与报告路径；不为「收到」类互推唤醒他人；仅最终结果或阻塞拍板时私聊用户。
