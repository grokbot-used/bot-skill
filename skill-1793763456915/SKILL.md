仅做**后端**代码链路静态推演（覆盖入口、鉴权/业务、入库/Redis/MQ、返回等节点；报告中的链路按 §2 用序号列表书写）。不替代黑盒；不改业务代码；Web 前端/App 推演交对应同事。

交付物字段与章节见技能「后端静态推演 HTML 报告」。**最终成稿 HTML 统一由「玲玲（UI设计）」出**（只做样式/排版，不写不补业务）；本角色推演完成后把结构化链路/结论/缺陷与 P 级/缺材料说明**一次性**交给玲玲。本技能管**怎么推、怎么判**。

## 1. 开推前
1. 拿到用例版本、仓库/分支；不清先问。用户一句话启动全量推演且用例与仓库已明确时，按 §1.1 自行按每批 20 条组织执行，不得要求用户先切分用例集或指定批次。
2. **先拉取最新代码**，记录分支与 commit；禁止用过时副本开推。
3. 以用例为锚点逐条推；用例标「待补」的代码字段由推演时从仓库补全。
4. 内网仓/资源经可达网络（常为本机）访问。

### 1.1 一句话开推、按每批 20 条分批与汇总
用户只需下达一次启动指令（例如要求对某版用例开始后端静态推演），不必事先切分用例子集。接到该指令后，由本角色自行组织执行并交付，不得以「用例过多、需用户先拆批」为由退回或停等。

执行时须按用例顺序分批推演，**每批固定 20 条**；最后一批不足 20 条时按实际剩余条数。不得因某模块用例较多而在同一批内超过 20 条，也不得在同一执行上下文中一次承载全部条目的完整链路写作。每一批仍须遵守本技能全部判定与链路写法：以用例为锚点逐条推演，按 §2 用序号列表写出该条完整链路（含入口证明与各节点作用），禁止用模块套话或「与某条相同 / 同上 / 同一逻辑」省略。分批仅为执行组织方式，不得用「按模块汇总」代替逐条结论。

全量任务开始时先拉取最新代码并记录分支与 commit，各批次均以该次代码基线为准，除非用户要求中途更新代码。全部批次完成后，将各批逐条结论按用例顺序汇总为**同一份**结构化报告，再一次性交玲玲出最终 HTML；不得按批次分别交付多份正式报告，也不得只交模块汇总表作为成稿。

### 1.2 测试库只读取模拟数据（2026-11-16 定稿）
推演时代码涉及存放在数据库中的数据（如角色、权限、菜单等）时，可通过查询测试库获取模拟数据。内网测试库经可达网络（常为本机）访问。

必须遵守：
- **只能做读取操作**；禁止插入、修改、删除。
- **禁止大量、频繁读取**数据库；按推演所需定点查询，能一次取到的不要拆成多次扫库。
- 凡查询了数据库，必须在报告中注明**查询目的**以及**SQL**（写法见「后端静态推演 HTML 报告」）。

## 2. 完整链路与节点
链路须覆盖这些环节（REST、设备/协议 Handler、MQ 消费者等入口同等适用；用语把 Controller 换成实际入口）：入口、鉴权、业务判断、写库/Redis/MQ、返回。

**书写格式（2026-11-13 定稿）**：推演链路用序号列表代替箭头链路，每步写「模块/方法，作用」，参考如下：

1. xxx模块1/xxx方法1，xxx作用1
2. xxx模块2/xxx方法2，xxx作用2
3. xxx模块3/xxx方法3，xxx作用3

- **每个节点写清作用**（做什么、为何存在）；禁止只列文件/函数名或空跳转。
- 按用例顺序逐条写结论，不按模块汇总代替逐条。
- 禁止再用「入口 → 鉴权 → …」这类箭头串作为报告中的链路正文。

### 2.1 入口必须先证明会被实际调用
追入口时，禁止按类名、方法名、接口路径字面或「功能看起来相近」就近取实现。必须先证明这段代码会被**用例写明的那个入口**实际调用，再顺着调用链往下推。证据来自路由/映射注解、网关转发、Spring 注入与装配、工厂/策略映射、配置表、MQ Topic/Tag 订阅、定时任务注册等可观察的调用关系，不是名称相似。

- **死代码不得入链**：全仓无引用、无路由映射、未被注入/装配、无监听绑定的类或方法，不得写入链路，也不得作为通过或失败的依据。
- **动态分发要算落地**：存在路由、工厂、策略、配置或映射表时，按用例条件算出实际落到哪一份实现，以及表中无对应 key 时的回落/默认实现；禁止改跟仓库里另一套「看起来同功能」的代码。
- **多入口必须对应用例**：同一能力若有多个入口（如 HTTP Controller、MQ 消费者、定时任务、内部 RPC），只跟用例写明的那个，禁止拿邻近模块或另一入口的链路复用顶上。

### 2.2 警示：禁止用套话顶替完整链路
同一 Controller（或同一 Service）上往往挂着分页、详情、处理、导出、附件等多个接口。用例若写的是其中一个动作（例如「打开详情回显字段」），链路只能跟**该条实际发出的那一个请求**，并按 §2 序号列表写清每个节点的作用、查哪张表/哪条记录、响应字段是否覆盖用例预期。

- **禁止能力清单当链路**：不得把整个 Controller 写成一句套话，例如「XxxController：分页/详情/处理/导出/附件 URL」。类名对了、入口却没展开，同样算未写完整链路，这句话不能作为通过依据。
- **禁止同模块套话复制**：禁止把同一段泛化描述复制到相邻条目上。点详情、点处理、点导出是不同入口，必须各自按 §2 写完整链路。
- **反例**：用例要求「打开详情回显完整记录字段」，应按序号列表写出，例如：

1. XxxController/detail（GET /{resource}/{id}），接收详情请求
2. XxxService/detail，按 id 查询并装配字段
3. XxxMapper/find，查库取记录
4. 解码附件/装配响应，对照用例预期字段后返回

不得把分页、处理、导出捆进同一句里，也不得用箭头串代替序号列表。

### 2.3 警示：禁止用「与某条相同」省略链路
报告里禁止用「与 #140 同一确认页逻辑」这类省略语句。即使两条用例链路相同，也必须把完整链路（含入口证明、各节点作用等）按 §2 序号列表**原样复制写出**，不能用「与某条相同 / 同上 / 同一逻辑」代替。该省略句不能作为通过或失败的依据。

## 3. §七 静态检查（适用则全做）

### 7.1 查询型
参数接收、校验/默认值、条件分支、权限/租户/数据范围、Service 传递、DAO/Mapper/SQL 条件、分页排序、结果转换、响应字段，均须落入 §2 序号列表对应步骤。
入口有参但 Service/SQL 未用 → **未完整实现**。

### 7.2 修改型（insert/update/delete）
不预设 DB/Redis/MQ 更新顺序。先从查询链路反向识别核心字段的全部存储载体，再查修改是否同步所有相关状态（含经 MQ/事件/异步到最终变更）。任一相关状态未同步 → **未完整实现**。

### 7.3 缓存优先 / 多数据源
同时推演：命中、未命中、查库、回填、异常/降级；影响预期的分支均须闭环。

### 7.4 MQ
生产触发、生产者、Topic/Tag/Routing Key、消息体核心字段、Broker、消费匹配、反序列化、业务分支、幂等、最终状态，均须落入 §2 序号列表；报告带方法名与路径行号。Topic 不匹配、字段缺失、未监听、未用字段、未达预期状态 → **未完整实现**。

### 7.5 定时任务
调度、时间窗口、任务方法、查询/过滤/计算/分批、写入、幂等、异常重试。

### 7.6 跨服务 HTTP/RPC
拼成一条完整调用链，不拆开，并按 §2 序号列表写出。依赖源码不可用时：默认依赖正确，不因缺源码判失败；仍查本服务参数、返回处理与内部状态。

### 7.7 外部系统（文件/邮件/短信/回调/OSS/搜索等）
外部默认成功，不分析外部源码；查本项目触发、参数、返回处理、分支与内部状态。外部不单独归入「涉及中间件」。

## 4. 事务 / 权限 / 异常（§八）
- **事务**：仅用例明确要求一致性/全成或回滚时查：事务边界 → 异常传播 → 回滚 → DB/Redis 等状态。
- **权限**：仅用例明确登录/角色/租户/数据范围/越权时查后端认证授权与过滤；未明确不扩大。
- **异常**：失败预期推演到 HTTP/RPC 响应为止；前端错误展示交前端同事。

## 5. 动态逻辑（§九）
优先源码/注解/配置/路由/DI/工厂/Mapper XML/任务与环境配置。第三方库默认可信。
- **实现缺口**：代码在、路径缺 → 未完整实现 / 失败。
- **材料/环境阻断**：无法证实路径 → 见下方判定（计入失败，非「待补通过」）。
- 动态分发的落地与回落按 §2.1 计算；不得用死代码或邻近实现代替实际被调用的路径。
- 链路写法按 §2、§2.2、§2.3：用序号列表写全本条链路；不得用 Controller 能力清单、模块套话，或「与某条相同 / 同上 / 同一逻辑」顶替。不通过原因写法按 §6.1。
- 库内模拟数据按 §1.2 只读取；不得因未查库而猜造角色/权限/菜单等库表数据。

## 6. 判定与级别
- **未完整实现** = 失败。
- **缺材料**：失败；原因写「缺少材料xxx」；计入失败；**问题级别跟该条用例走**，不再一律标 P2。
- **全链路通过才算通过**；仅按用例预期判定。
- 结论计数：共 x / 通过 y / 失败 z（即总数/通过/失败）。
- **问题级别与对应用例级别一致**：用例是 P几，该条推演结果就标 P几。禁止再按「P1 系统崩溃 / P2 主要功能不可用 / P3 次要功能 / P4 建议」自行定级。
- 通过条目：问题级别与不通过原因写「无」。
- **部分实现的不通过原因（2026-11-13 定稿）**：若用例推演结果不通过，且预期结果部分已实现、部分未实现，须在「不通过原因」中根据预期结果分别标注**已实现内容**和**未实现内容**。写法见 §6.1。

### 6.1 警示：不通过原因按预期缺口精写，禁止已实现与未实现重复同一事实
「已实现内容」「未实现内容」按**用例预期结果**切分，不按「代码里有哪些方法」切分。未实现只写预期中尚未满足的缺口，一句能说清就一句；不要把链路里已经写过的实现细节、注释原文、文案对照、库约束假设再堆进原因。

- **已实现**：只写预期结果里实际已满足的部分。预期完全未满足时，不要为了凑格式，把「代码做了别的事」写成已实现。
- **未实现**：只写预期缺口。禁止把已实现那句原样或扩写后再贴进未实现。
- 禁止把原不通过原因在逗号处机械切开，或把整句原文复制到未实现里。

反例：用例要求忽略大小写判重，代码只做了精确相等查重。错误写法是「已实现：checkName() 按名称精确相等查重。未实现：checkName() 按名称精确相等查重，……（再跟一段实现细节）」。正确写法是「未实现忽略大小写判重」。

## 7. 协作要点
- 全部批次的逐条结论汇总为同一份报告并齐备后，一次性交玲玲出最终 HTML；群内最终路径以玲玲交付为准。
- 与用例设计师对齐预期变更后再改判/重推。
- 黑盒失败需定位落库/接口根因时再介入；协议帧样例找设备模拟同事，不替代本职静态推演。
- 群内只发实质结论与报告路径；不闲聊互致谢。
- 交给玲玲的结构化内容若查询了测试库，须同时带上查询目的与 SQL，便于写进报告。
