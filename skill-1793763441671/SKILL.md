# 前端静态推演报告（HTML）

通用模板：只做 **浏览器 Web 前端**（HTML/CSS/JS 与常见 Web 框架）静态推演；不改业务代码、不跑应用/浏览器实机、不做后端实现推演、不编造读不到的链路。

## 1. 开工前
1. **先拉取最新代码**（约定分支），确认 `HEAD` short commit 后再推演；基线写入报告材料。
2. 锚点用例、需求/范围不清时先问清；无页面入口（如仅 Job/TD-only）可只追到请求或整段跳过。
3. 有页面入口的用例：一律追到 **返回处理与数据展示**（用例只验请求不验展示时可不验展示）。
4. **入口须从实际挂载组件追起**：先核引用/路由/动态映射与回落；全仓无引用的文件不得作为路径或判定依据（详见「Web前端静态推演流程」§ 2.1）。
5. **全量推演工作流**：用户只需一句话下令开始推演，不必事先切分用例子集；接到指令后自行组织执行，不得要求用户先拆批。按用例顺序每批固定 20 条逐条推演（末批不足 20 条按剩余条数）。全部批次完成后，按用例顺序汇总为同一份报告再交玲玲。分批仅为执行组织，不得用模块汇总代替逐条结论，也不得按批次分别交付多份正式报告。

## 2. 检查目标（Web 前端段）
- 用户交互、页面状态、数据请求、返回结果处理、数据展示、前端自行负责的边界与业务判断。
- **交互链**（检查顺序，落笔见 §3）：页面/组件 → 可见可操作 → 事件绑定 → 校验 → 条件判断 → 状态变化 → API → 返回处理 → 刷新/跳转/提示。
- **展示链**：响应字段 → 转换/适配 → 状态 → 列表/表单/详情绑定 → 格式化/枚举/条件渲染 → 用户所见。
- **边界**：用例要求的长度/范围/必填/格式/空值/重复提交/禁用/分支/错误提示；即使用例未写明，若仅后端校验而前端仍可提交非法输入 → **未完整实现=失败**。
- **异常路径**：预期含校验失败/业务异常/权限拒绝/错误提示时，异常路径即目标链路，追到错误处理与页面状态。
- **权限**：用例明确涉及登录/角色/租户/越权时才查前端权限（隐藏/禁用/路由守卫）；未明确不扩大。
- **动态逻辑**：优先读源码/配置/路由/映射；缺关键配置或运行时数据 → 未完整实现。第三方库默认可信，只查项目封装与返回处理。
- **文案/i18n**：若项目构建时注入翻译（如 `pull_translations`），**不以仓库语言包缺 key 判露文案失败**；区分仓库静态与构建后现网。

## 3. 调用链写法
（2026-11-13 起）「链路推演」用**序号列表**写出，**不再用箭头（`→`）串联**。每步写「模块/方法，作用」，并带源码路径与行号。参考如下：

1. xxx模块1/xxx方法1，xxx作用1
2. xxx模块2/xxx方法2，xxx作用2
3. xxx模块3/xxx方法3，xxx作用3

节点须写清做什么、为何存在；禁止只列文件/函数名或空跳转。典型顺序仍是：入口、事件绑定、条件判断、请求、返回处理、展示。入口节点必须是实际挂载的组件，不得写全仓无引用的死代码。

**禁止省略完整链路**：即使两条用例链路相同，也必须把完整链路（含入口证明、各节点作用、路径行号等）原样复制写出。不能用「与某条相同 / 同上 / 同一逻辑 / 与 #140 同一确认页逻辑」代替。每条的「链路推演（含入口证明）」都必须是自包含的完整文本。禁止用模块套话代替逐条链路。

## 4. 通过 / 失败 / 级别
- **未完整实现** = 失败，计入失败数。
- 读不到源码或缺关键文件 → 失败，原因「缺少材料xxx」；**问题级别与该条用例级别一致**，不再一律标 P2。
- **问题级别与对应用例级别一致**：用例是 P几，该条推演结果就标 P几。不要再按「P1系统崩溃 / P2主要功能不可用 / P3次要功能 / P4建议」自行定级。通过条目的级别与原因为「无」。用例未标级别时先问清，不得自行补级。
- **全链路通过才算通过**；仅按用例预期判定。
- 结论：**x / y / z = 总数 / 通过 / 失败**；跳过另计并写清。不把未推演写成通过。
- **不通过原因的已实现 / 未实现（2026-11-13 起）**：用例推演结果不通过，且预期结果部分已实现、部分未实现时，在「不通过原因」中分别标注**已实现内容**和**未实现内容**。切分依据是**用例预期结果**，**不按代码里有哪些方法切分**。
  - **已实现**：只写预期结果里实际已满足的部分。预期完全未满足时，不要为了凑格式，把「代码做了别的事」写成已实现。
  - **未实现**：只写预期中尚未满足的缺口，一句能说清就一句。禁止把已实现那句原样或扩写后再贴进未实现。不要把链路里已经写过的实现细节、注释原文、文案对照、库约束假设再堆进原因。
  - 禁止把原不通过原因在逗号处机械切开，或把整句原文复制到未实现里。
  - 反例：用例要求忽略大小写判重，代码只做了精确相等查重。错误写法是「已实现：checkName() 按名称精确相等查重。未实现：checkName() 按名称精确相等查重，……（再跟一段实现细节）」。正确写法是「未实现忽略大小写判重」。

## 5. 交付与玲玲成稿
- **最终成稿 HTML 统一由「玲玲（UI设计）」出**：玲玲只做样式/排版，不写不补业务内容。
- **全量推演只交一份正式报告**：全部批次完成后，按用例顺序汇总为同一份再一次性交玲玲；不得按批次分别交付多份正式报告，也不得用模块汇总代替逐条结论。
- **文件名只能三字段**：`报告能力_需求名_版本号.html`，例：`前端静态推演_价格管控OpenAPI_v1.0.2.html`。**禁止**再加阶段/优先级等其它字段（如 `_P2_`）；版本号往上叠；特殊说明写正文备注。
- 文内必须含 **报告生成时间**：`yyyy-mm-dd HH:MM:SS`（Asia/Shanghai）。
- **失败清单摘要（2026-11-13 起）**：只对整体失败用例做简单概述说明；**删除（不再写）每条失败用例说明**。逐条失败原因仍写在各条「不通过原因」中，不要搬进摘要逐条展开。
- 推演完成后，一次性交给玲玲的结构化材料须含：
  - 文首：需求、基线（仓库路径/分支/commit）、范围、方法、结论（总数/通过/失败[/跳过]）
  - 失败清单摘要：对整体失败用例的简单概述（不逐条罗列说明）
  - 逐条：用例编号、链路推演（序号列表；每步「模块/方法，作用」+路径行号；须自包含完整写出，禁止用「与某条相同/同上」省略）、推演结果、问题级别（与该条用例级别一致）、不通过原因（部分实现时须按预期结果分标**已实现内容**与**未实现内容**；切分不按代码方法，未实现只写预期缺口且勿堆链路细节）、备注/证据
  - 筛选项约定：推演结果（全部/通过/失败/跳过）、问题级别（全部/无/P1/P2/P3/P4，填写时与该条用例级别一致）
  - 建议文件名严格按三字段；交玲玲成稿时按此命名
- 自己可保留推演草稿便于核对，但**对外/群内最终 HTML 以玲玲成稿为准**，不自行交付最终排版版。
- 标题约定：**前端推演报告（静态）**。只写 Web 前端段；路径里没有的调用链不许编造。
