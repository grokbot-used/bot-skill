# APP 静态推演报告内容规范

按已审核用例整理 Android / iOS **原生**静态推演的报告内容。不含 Web 前端、小程序、整条非原生跨端栈。

**成稿分工**：推演侧只产出**完整业务内容**（链路/结论/缺陷与优先级）；**最终 HTML 成稿**统一交团队指定的报告 UI/排版同学生成（对方只做样式/排版，不写不补业务）。全量推演分批仅为执行组织；全部批次完成后，按用例顺序汇总为**同一份报告**再一次性交接，勿拆条多次，也不得按批次分别交付多份正式报告。

## 1. 开始前

1. 确认用例已过审核、用户已开推演步骤；材料不足先列缺口，不臆造。按技能「推演分工名单」执行：须有三端共识且经用户审核通过的名单；开推前向用户确认本次代码仓库后再拉代码。名单未通过审核或仓库未确认前不得开推。用户只需一句话下令开始推演，不必事先切分用例子集；接到指令后自行按用例顺序每批 20 条组织执行（末批不足 20 条按剩余条数），**不得要求用户先拆批**。全文见该技能，本技能不复制条文。
2. **先拉取目标仓库/分支最新代码再推演**（用团队约定的拉码方式；本地不擅自改业务代码）。
3. 明确：需求名、基线版本、仓库与分支、平台范围（Android / iOS / 双端）、入口页面或控件。

## 2. 推演范围与链路

### 入口证明（跟线前必做）
追入口时**不能**按类名、界面名或功能名就近取实现，必须**先证明**该 Activity / Fragment / UIViewController 会被用例对应的入口实际打开（如 Intent 与 Manifest 注册、Navigation Graph、ARouter path；或 Storyboard/segue、`push`/`present`、路由注册表）。

- 工程里**无引用**、未注册到清单或导航的类或界面是**死代码**，不得作为推演路径，也**不得作为通过或失败的依据**。
- 有路由、工厂、配置或动态映射时，按**用例条件**算出实际落到哪一份实现及无匹配回落，不跟「看起来同功能」的另一套。
- 同一能力若有多入口，必须跟**用例写明的那一个**，不能拿邻近模块链路复用顶上。
- 证不清实际打开的目标时：按缺材料口径判失败，不得用就近实现抵消。
- 链路推演文中须写清入口证明（从哪个控件/事件发出何种跳转，落到哪个已注册界面）。

### 核心检查
用户交互；页面/界面状态；数据请求；返回结果处理；数据展示；客户端自行负责的边界与业务判断。

### 交互全链路（须完整追踪）
以下为须覆盖的环节（写法见「节点写法」的序号列表，不用箭头串联）：Activity/Fragment 或 UIViewController；控件可见；可操作（enabled / userInteractionEnabled）；事件绑定（setOnClickListener、IBAction、手势等）；客户端校验；条件判断；状态变化（ViewModel/LiveData/StateFlow 或 Combine/闭包等）；网络调用（Retrofit/OkHttp/URLSession 等）；返回结果处理；UI 刷新 / Intent·路由跳转 / Toast·Dialog·Snackbar / 控件状态更新。

### 数据展示链路
接口响应字段经客户端转换后，绑定到列表/详情等控件。

### 节点写法
链路推演用**序号列表**写出，不用箭头串联。每步写「模块/方法，作用」，参考：

1. xxx模块1/xxx方法1，xxx作用1
2. xxx模块2/xxx方法2，xxx作用2
3. xxx模块3/xxx方法3，xxx作用3

每个节点写清：**做什么、为何存在**；「模块/方法」须可定位（文件/类/方法）。禁止只列文件名或空跳转；路径里没有的调用链不许编造。

**禁止省略语代替完整链路**：即使两条用例链路相同，也必须把完整链路（含入口证明、各节点作用与定位等）**原样复制写出**。禁止用「与 #xx 同一确认页逻辑」「与某条相同」「同上」「同一逻辑」等省略语句代替本条链路推演。

### 跨端桥
RN / Flutter 等：只追到**原生桥入口**并标缺口，交跨端同学；整条非原生栈不硬推、不擅自判实现缺陷（缺材料时按判定节处理）。

### 事务 / 权限 / 异常（用例明确才扩大）
- 一致性：失败后 UI/本地缓存是否部分写入、是否与失败响应联动。
- 业务权限：登录/角色/数据权限/越权、入口隐藏、拦截器·路由守卫、Token 等；**系统权限（相机/定位/通知等）不纳入业务权限必查**。
- 异常：追到客户端错误处理与提示/界面状态。

### 动态与不确定
优先源码与配置；动态路由/反射/模块加载等关键运行时信息缺失 → **未完整实现**（= 失败）。第三方库默认可信，只查项目自定义代码与参数/返回值处理。

## 3. 判定

- **优先级与对应用例优先级一致**：用例是 P几，该条标题左侧就标 P几（通过条目也展示，不要写「无」）。不要再按「P1 系统崩溃 / P2 主要功能不可用 / P3 次要功能 / P4 建议」自行定级。逐条不再单列「问题级别」字段（通过时也不再写「无」）。
- 读不到源码 / 绑不到事件 / 桥缺口 / 缺配置等 → **失败**，原因「缺少材料xxx」；标题左侧优先级**跟该条用例走**，不再一律标 P2；不另开「无法判定」。
- **未完整实现 = 失败**。
- 只有**全链路通过**才算该条通过；其余一律失败。
- 若推演结果不通过：在「不通过原因」中按**用例预期结果**切分**已实现内容**和**未实现内容**，不按代码里有哪些方法切分。
  - **已实现**：只写预期结果里实际已满足的部分。预期完全未满足时，不要为了凑格式，把「代码做了别的事」写成已实现。
  - **未实现**：只写预期中尚未满足的缺口，一句能说清就一句。不要把链路里已经写过的实现细节、注释原文、文案对照、库约束假设再堆进原因。禁止把已实现那句原样或扩写后再贴进未实现。
  - 禁止把原不通过原因在逗号处机械切开，或把整句原文复制到未实现里。
  - 示例：用例要求忽略大小写判重，代码只做了精确相等查重。错误写法是「已实现：checkName() 按名称精确相等查重。未实现：checkName() 按名称精确相等查重，……（再跟一段实现细节）」。正确写法是「未实现忽略大小写判重」。
- 结论 `x/y/z` = **推演总数 / 通过数 / 失败数**（仅可推条目）。有跳过另记跳过条数，不计入「共」。不再另记「不测」。没标「app」的，或用例本身标注不测的，一律记跳过，备注写明原因（名单中由哪端负责，或用例不测）；跳过条目按用例顺序保留。
- **仅按用例预期**判通过/失败；用例未写的异常不因此判该条不通过，可另记建议（不改写本条优先级）。

## 4. 文件名与时间（交给排版时按此约定）

- 最终成稿为 **HTML**（未特别指定时）。
- 文件名**只能三字段**：`报告能力_需求名_版本号.html`，禁止加其它字段。示例：`APP静态推演_需求名_v1.0.0.html`。
- 版本号往上叠；特殊说明写**正文备注**，不塞进文件名。
- 文内须有**报告生成时间**：`yyyy-mm-dd HH:MM:SS`（Asia/Shanghai）。

## 4.1 成稿排版约定（交排版同学时一并说明）

- 逐条删除「问题级别」字段（通过时也不再写「无」）。
- 在每条标题左侧增加「优先级」，用气泡/徽章样式，取值与该条用例的优先级保持一致（用例是 P几就标 P几；通过条目也展示用例优先级，不要写「无」）。不要再自行按崩溃/主要功能定级。
- 过滤/搜索栏原「问题级别」改为「优先级」，支持多选。
- 「导出表格」CSV 对应列由「问题级别」改为「优先级」。
- 跳过条目按用例顺序保留，结果展示为「跳过」，不改名为「不测」；跳过不计入结论「共」，另记跳过条数。

## 5. 须交接的结构化内容（文首 + 逐条）

### 文首字段
- 标题（如「APP 静态推演报告」）
- 需求、基线、仓库/分支、范围、方法（静态读码链路推演）
- **参与人**（谁参与、各自负责；本能力写清负责 App 原生静态推演：入口、事件、条件、请求、返回、UI/展示与边界）
- 结论（x/y/z；有跳过另记跳过条数，不计入「共」，不再另记「不测」）
- **失败清单摘要**：对整体失败用例做简单概述说明；**不要逐条写各失败用例说明**。逐条不通过原因仍写在正文各条的「不通过原因」中。
- 报告生成时间（若已定）
- 备注（特殊说明，若有）

### 正文（按用例顺序逐条，禁止用模块汇总代替）
全量推演分批执行后，正文仍按**用例顺序**汇总进**同一份**报告，不得按批次拆成多份正式报告，也不得用模块汇总代替逐条结论。
跳过条目仍按用例顺序保留在正文中：推演结果记「跳过」，备注写明原因（名单中由哪端负责，或用例不测），不写「不测」；跳过条只保留编号、标题（含优先级徽章）、推演结果「跳过」及原因备注，不必写完整链路、请求与不通过原因。
每条至少含：
1. 推演用例编号及标题；标题左侧带「优先级」气泡/徽章，取值与该条用例优先级一致（用例是 P几就标 P几；通过条目也展示，不要写「无」）。不要再自行按崩溃/主要功能定级。逐条不再单列「问题级别」字段（通过时也不再写「无」）。
2. **链路推演**（含入口证明；按第 2 节全链路覆盖；用序号列表写每步「模块/方法，作用」，不用箭头串联）；**必须本条写全**，禁止用「与 #xx 同一确认页逻辑」「与某条相同」「同上」「同一逻辑」等省略语句代替。即使与另一条链路相同，也要把完整链路（含入口证明、各节点作用等）原样复制写出。（跳过条不必写链路。）
3. 终点请求（若有）：URL / 方法 / 关键参数
4. 返回处理与 UI/数据展示要点
5. 推演结果（通过 / 失败 / 跳过）
6. 不通过原因（失败时必填；缺材料写「缺少材料…」；写法见第 3 节：按用例预期结果切分已实现与未实现，不按代码方法切分。已实现只写预期中已满足的部分；预期完全未满足时不要把「代码做了别的事」写成已实现。未实现只写预期缺口，一句能说清就一句，不把链路里已写过的实现细节、注释原文、文案对照、库约束假设再堆进原因；禁止把已实现那句原样贴进未实现，禁止把原不通过原因在逗号处机械切开或把整句原文复制到未实现里；跳过条改写原因备注，不写不通过原因）
